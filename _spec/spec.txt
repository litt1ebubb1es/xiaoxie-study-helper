| 本文提出一款运行在本地的网课学习助手，课程无论运行在浏览器中还是专用客户端里，都由同一套采集底座支撑。它不替用户记笔记，也不替用户答题，而是持续判断“这一刻你有没有听懂”，并在你没听懂的位置提供有针对性的重讲。系统的核心是一套卡点识别算法：用统计算出内容的认知负荷，用播放行为判断用户的真实反应，两者交叉形成四象限判定，再通过事后证据、抽样自测与跨课对账确认那些用户自己都没有察觉的知识漏洞。 整套方案建立在华硕 ProArt N1X（NVIDIA RTX Spark N1X 平台）的本地算力之上。选择端侧不是出于成本偏好，而是因为这类系统需要长期积累个人学习档案、需要处理包含师生影像的课堂画面、需要在听课全程保持零边际成本运行，这三条在云端架构下都不成立。 本方案包含产品定义、端侧必要性论证、系统架构、卡点识别算法、数据模型、关键设计决策记录、合规边界与实施计划，可直接作为工程落地依据与参赛技术说明。 |

一、项目概述
1.1 核心命题
在线学习真正困难的地方，在于没有人知道你从哪一刻开始跟不上了。
线下课堂里，老师能看见学生的表情；学生听不懂时会皱眉、会翻书、会小声问同桌。网课把这条反馈回路彻底切断了。学生面对的是一个匀速播放的视频，它不会因为你没听懂而停下，也不会因为你已经会了而加速。
现有工具解决的都是“信息加工”问题：录屏、转写、总结、做脑图。它们默认学生已经把内容听进去了，剩下的只是整理。但真实的失败点往往更早——内容根本没进入理解，整理出来的笔记只是把没听懂的话抄了一遍。
因此本项目的切入点不是“帮你整理”，而是帮你发现没听懂的地方，并把它讲明白。我们把这样的位置称为卡点。
一个卡点由三要素构成：时间位置（第几分几秒）、认知缺口（缺的是哪个概念或哪一步推理）、成因（是前置知识缺失、讲法不匹配，还是信息密度过高）。系统围绕这三要素组织全部功能。
1.2 目标用户
<<TABLE>>
| 用户类型 | 典型场景 | 核心痛点 |
| 在校大学生 | 专业课录播、通识课、实验课 | 一节 90 分钟，回看成本高，考前不知道漏洞在哪 |
| 考证与考研人群 | 长周期系统课，动辄上百小时 | 进度压力大，遇到难点容易整段放弃 |
| 职业学习者 | 技术课程、行业培训 | 术语密集，前置知识断层，缺乏可提问的对象 |
<<END TABLE>>
三类用户的共同特征：课程时长长、内容密度高、没有实时答疑渠道。这决定了系统必须能长时间静默运行，并且能对长内容做结构性分析。
1.3 设计原则
第一，静默优先。听课过程中不弹窗、不总结、不打断。所有理解与整理在课后完成。
第二，检测与理解分离。轻量判断常驻，重量分析按需。这条原则决定了系统在消费级硬件上是否可行。
第三，克制能力边界。不代写作业、不代答题、不接管播放。产品价值建立在“帮用户听懂”，而非“帮用户完成”。
第四，数据留在我这里。课堂音频、屏幕画面、学习行为一律不出本机。
二、为什么必须端侧
大赛要求“开发能发挥端侧优势的 AI 应用”。一个诚实的做法是先证明：如果把同样的系统搬到云端，它会坏在哪。
2.1 三条硬约束
约束一：成本结构不成立。一节 45 分钟的课会产生约 6000 至 8000 字的转写文本，以及全程的屏幕帧与行为事件。系统需要对这些内容做持续判断，并在课后做多轮分析。按主流云端 API 的按量计费模型，一名学生一天四节课的持续调用成本会远超其对工具的付费意愿。而本地运行的一次性硬件投入之后，边际成本只剩电费。
约束二：隐私边界不可让渡。网课画面里会出现授课教师的形象、同学的头像、聊天区的真实姓名，音频里可能出现宿舍环境声与私下对话。把这些内容上传到第三方服务器，本质上是把他人的影像与声音交出去，这不是用户单方面同意就能解决的事情。本地处理是唯一干净的解法。
约束三：交互延迟不可接受。卡点标记需要在用户回退后数秒内出现在时间轴上，实时字幕需要亚秒级跟随。任何依赖网络往返的架构都在这条线上失守。
2.2 一个不可替代的理由
前三条约束都可以被反驳——“云端也能做，只是贵一点、慢一点”。真正无法反驳的是第四条：
<<TABLE>>
| 这套系统的核心资产是跨课程、跨学期的个人学习档案，它必须生长在用户自己的机器上。 |
<<END TABLE>>
隐性卡点的判定依赖“这个概念在后面被再次提及时你的反应”，结构性卡点依赖“三节课都卡在同一类前置知识”。这些判断需要数月的数据积累。云端方案要么无法长期留存这些高度敏感的行为数据，要么留存了也无法与本地设备的其他上下文（本地文件、本地笔记、本地做题记录）打通。
换句话说：这套系统会随着使用越来越懂你，而这份“懂”存在你的电脑里，不在别人的服务器上。这是端侧方案的结构性优势，不是成本优势的另一种说法。
2.3 方案对比
<<TABLE>>
| 维度 | 云端 API 方案 | 本地 N1X 方案 |
| 单节课分析成本 | 按 Token 持续计费，长课程迅速累积 | 一次硬件投入，边际成本近零 |
| 课堂影像与音频 | 必须上传，涉及第三方隐私 | 全程不出本机 |
| 卡点标记延迟 | 受网络往返与排队影响 | 本地毫秒级 |
| 长期学习档案 | 受留存政策与服务可用性约束 | 永久留存，可与其他本地数据关联 |
| 离线可用 | 不可用 | 完全可用 |
| 模型能力上限 | 可调用更大模型 | 122B 级开源模型，质量接近云端中高端 |
| 高峰并发 | 受配额限制 | 无限制 |
<<END TABLE>>
结论：本地方案在成本、隐私、延迟、长期资产四个维度上占优，仅在“极端峰值能力”上略逊。对本场景而言，这个取舍是划算的。
三、产品设计
3.1 功能全景
系统由四个功能构成，围绕卡点形成闭环。
<<TABLE>>
| 编号 | 功能 | 定位 | 优先级 |
| F1 | 卡点识别 | 自动发现没听懂的位置 | P0 |
| F2 | 划段重讲 | 对指定时间段做降维重讲 | P0 |
| F3 | 截图对回课程 | 把题目映射回课程知识点与时间点 | P1 |
| F4 | 漏洞地图 | 汇总卡点，生成复习路径 | P1 |
<<END TABLE>>
四者的关系是：F1 发现问题，F2 解决单点问题，F3 解决“题目不会做但说不清哪儿不会”的问题，F4 把单点问题汇总成结构性诊断，并成为下一轮学习的起点。
3.2 F1 卡点识别
系统在听课过程中静默采集三类信号，在时间轴上连续打分，产出卡点候选。用户也可以随时手动标记，手动标记的权重高于任何自动信号。
识别结果分三种状态：显性卡点有明确行为证据（回退、反复播放），直接进入待解决队列；隐性卡点候选指内容负荷高但当时无异常行为，等待后续证据确认；结构性卡点指跨多节课在同一类前置知识上反复出现，标记为根因级问题。
3.3 F2 划段重讲
用户选中一段时间范围（或直接点击某个卡点），系统重新处理该段音频并重讲。关键设计是：重讲不是复述，而是降维。
系统提供五种重讲策略，用户可选择，系统也会根据内容类型自动推荐。
<<TABLE>>
| 策略 | 做法 | 适用场景 |
| 换类比 | 用一个生活化场景替代原讲授路径 | 抽象概念、数学定义 |
| 补前置 | 指出缺失的前置知识并先讲它 | 卡在推导中间步骤 |
| 数值化 | 用具体数字代入跑一遍 | 公式、算法、财务模型 |
| 反向验证 | 从结论倒推，解释为什么会得到它 | 定理证明、架构决策 |
| 分层复述 | 先给一句话版本，再逐层加细节 | 信息密度过高的段落 |
<<END TABLE>>
重讲时系统会带着三个上下文：这一段之前讲了什么、这一段之后要讲什么、用户此前在哪些相关概念上卡过。这让重讲能够落在用户真实的认知位置上，而不是做一次通用的重新解释。
3.4 F3 截图对回课程
用户在听课时遇到例题或看不懂的图表，可以框选屏幕区域提问。系统的处理链条是四步：识别截图中的题型与考查知识点；在当前课程的时间轴上检索讲该知识点最集中的段落；输出“这道题考的是 X，课程在第 23 分 15 秒讲过，当时的讲法是 Y”；如果该段讲解确实不足以支撑这道题，再做引导式补充。
核心差异在于第二步。通用 AI 能解题，但它不知道你四十分钟前听了什么。把题目和课程内容对上，是这个产品独有、且无法被通用助手复制的能力。
教育定位上，系统默认输出“这道题该往哪看”，答案本身放在可展开的第二层，避免产品退化为解题工具。
3.5 F4 漏洞地图
课后生成一份结构化诊断，包含四项内容：本节卡点清单（含时间点、知识点、成因分类）；卡点热度在课程时间轴上的分布；与历史课程的关联，即哪些卡点属于同一根因；建议的复习顺序，按前置依赖排序而非按时间顺序。
这份地图是系统的产出物，也是下一次学习的输入。它把“一次性问答”变成了“持续积累的学习档案”。
3.6 交互原则
不打断。这是本产品最重要的体验约束。
系统在听课时保持安静：不弹总结卡片、不提示“要不要帮你记一下”、不播报分析结果。所有工作在后台完成，课后一次性交付。
理由不只是体验。云架构的产品经理会本能地让每一次 API 调用都产出可见物，因为不产出就等于浪费钱。本地架构没有这个压力，因此可以真正做到“一直在跑，但不打扰你”。这本身就是端侧优势在产品设计上的体现。
四、系统架构
4.1 分层架构
系统自下而上分为六层，每层职责单一，层间以结构化数据交互。
接入层负责模型接入与切换。本地模型与云端 API 统一包装为 OpenAI 兼容接口，用户在设置中一键切换，上层逻辑不变。音频识别服务同样以 OpenAI 兼容的转写接口形式暴露，因此不需要为音频单开一条通道。
采集层负责信号获取，下设三个采集器：音频采集器（系统回环，可按进程分离）、画面采集器（按需截帧）、行为采集器（播放事件与进度推断）。三者对上暴露统一事件契约，因此上层的卡点算法完全不感知课程来自浏览器还是客户端，详见 4.2。所有采集均需用户首次授权，且不写盘原始音频（保留策略可配置）。
感知层负责把原始信号变成结构化数据。语音识别产出带词级时间戳的文本；说话人分离区分教师与提问者；语音理解补充情感与音频事件标签；视觉模块处理截图与低频画面；行为采集器把播放事件记为标准化事件流。
认知层负责核心判断。包括认知负荷计算、行为信号归一化、融合评分、四象限判定与隐性卡点确认。这一层以规则和统计为主，不依赖大模型，可在 CPU 上常驻。
生成层负责按需调用大模型。仅在用户触发重讲、截图问答、课后诊断时启动 122B 主脑。
存储层负责课程、转写、事件、卡点、知识点图谱的本地持久化。
4.2 采集覆盖面：浏览器与客户端统一
课程可能运行在浏览器里，也可能运行在专用客户端中。产品必须同时覆盖两者，否则大量课程无法进入系统。本方案的做法是：不按平台逐个适配，而在操作系统层采集。
判断依据很直接。在操作系统看来，浏览器里的视频和客户端里的视频没有区别，都只是一个进程在向声卡送音频、在屏幕上绘制画面。因此覆盖范围应当由采集底座决定，而不是由适配器清单决定。前者一次做完即覆盖全部，后者会随平台迭代无限膨胀。
<<TABLE>>
| 维度 | 浏览器网课 | 客户端网课 | 本方案处理 |
| 音频 | 可采集 | 可采集 | 系统音频回环，一视同仁 |
| 画面 | 可读 DOM，甚至能取字幕文本 | 只可得像素 | 窗口捕获 |
| 播放进度 | 精确，来自 video 元素 | 需推断 | 时间码 OCR、UI 自动化读进度条 |
| 播放行为 | 精确，seeking 与 ratechange 事件 | 需推断 | 高频采样与鼠标事件反推 |
| 字幕原文 | 部分可直读 | 不可得 | 一律以语音识别结果为准 |
<<END TABLE>>
在这个对照里，真正需要额外工作的只有最后两行，前三行的成本几乎为零。这意味着覆盖两种载体的边际成本远低于直觉判断。
三个采集器各有分工。音频采集器基于系统回环，并支持按进程分离，只取网课进程的声音，避免混入消息提示音与背景音乐；进程分离不可用时回落到整机回环并提示用户关闭其他音源。画面采集器按需截帧，仅在截图提问时使用高分辨率。行为采集器在浏览器中直接监听播放器事件，在客户端中则以时间码采样推断回退与暂停。
策略上采取渐进增强：第一版只做系统音频与行为推断，即可覆盖全部课程来源，不需要为任何平台单独开发；浏览器扩展作为可选的精度增强，安装后可获得精确进度与回退事件，不安装则功能完整、精度略降。这与其他环节的降级设计保持一致。
另外三条工程约束必须提前守住。其一，带版权保护的播放器会禁用画面捕获，此时系统自动降级为纯音频模式，核心能力不受影响。其二，进程级音频捕获对部分应用不生效，回落到整机回环即可。其三，只做外部观测，不向第三方进程注入代码或挂接内部函数，这既是技术选择，也是合规底线。
4.3 技术选型
<<TABLE>>
| 层 | 组件 | 说明 |
| 接入层 | 自研适配器 | 统一 OpenAI 兼容协议，屏蔽本地推理服务与云端 API 差异 |
| 采集层 | 系统音频回环（可按进程分离）、窗口捕获 API、UI 自动化与 OCR | 统一覆盖浏览器与客户端，无需逐平台适配 |
| 感知层 | Qwen3-ASR-1.7B、SenseVoice-Small、CAM++、Qwen3.5 视觉能力 | 详见 4.4 模型分工 |
| 认知层 | Python 规则引擎 + SQLite | 纯本地计算，无外部依赖 |
| 生成层 | Qwen3.5-122B-A10B（本地）或云端 API | 按需加载 |
| 存储层 | SQLite + 本地文件 | 单机单用户，无需分布式 |
<<END TABLE>>
4.4 模型分工
<<TABLE>>
| 任务 | 模型 | 规模 | 量化后占用 | 运行方式 |
| 实时转写 | Qwen3-ASR-1.7B | 1.7B | 约 2 GB | 常驻，流式 |
| 轻量兜底转写 | SenseVoice-Small | 234M | 约 0.5 GB | 按需，CPU 可跑 |
| 课后精转 | FireRedASR2 | 8.3B | 约 5 GB | 课后批处理 |
| 说话人分离 | CAM++ | 数十 M | 约 0.2 GB | 随转写调用 |
| 认知负荷辅助 | Qwen3.5-9B | 9B | 约 6 GB | 课后批处理 |
| 重讲与诊断主脑 | Qwen3.5-122B-A10B | 122B / 激活 10B | 约 75 GB | 按需加载 |
| 视觉理解 | Qwen3.5 视觉通道 | 随主脑 | 共享 | 按需 |
<<END TABLE>>
模型选择的依据不是“最强”，而是“够用且能同时驻留”。122B 主脑在 INT4 下约 75 GB，加上常驻的 ASR 与 9B 模型，峰值占用约 90 GB，128 GB 统一内存留有余量。
4.5 显存与算力预算
<<TABLE>>
| 场景 | 驻留模型 | 内存占用 | 说明 |
| 听课中 | ASR 1.7B + 辅助 | 约 5 GB | 极低占用，长时运行 |
| 课后批处理 | 上述 + 9B | 约 12 GB | 用户不在看课，可占满算力 |
| 重讲与诊断 | 9B + 122B 主脑 | 约 85 GB | 需从磁盘加载主脑，冷启约半分钟 |
| 夜间对账 | 9B | 约 8 GB | 空闲时段增量处理 |
<<END TABLE>>
关键工程点：122B 主脑不常驻。系统采用“按需加载 + 空闲卸载”策略，用户点击重讲时加载，闲置十分钟后卸载。这让听课阶段的资源占用保持在极低水平，也避免了长时间高温运行。
4.6 统一接入层
接入层是“本地也能用、API 也能用”这一诉求的落点，设计要点有四条。
协议统一。所有模型调用走同一套 OpenAI 兼容客户端，仅 base_url 与 model 名不同。
本地与云端等价。本地推理服务（如 vLLM、llama.cpp server、FunASR server）与云端 API 在协议层完全等价，切换对上层透明。
能力探测。启动时探测当前后端支持的能力（是否支持视觉、是否支持流式、上下文上限），不可用能力在界面上标注为“当前后端不支持”，而非静默失败。
降级策略。本地主脑加载失败时，可临时降级到云端 API 或本地 9B，并在界面上明确告知用户当前处于降级状态。
五、核心技术方案
5.1 音频管线：双遍转写
单一模型无法同时满足“实时”与“准确”两个目标：流式模型追求低延迟，精度有损；高精度模型体积大，无法实时。本方案按时间轴把两个目标拆开。
第一遍，实时流式。听课过程中使用 Qwen3-ASR-1.7B 流式识别，目标是让字幕跟上讲授节奏。允许个别字词错误，但要求时间戳稳定。
第二遍，课后精转。课程结束后使用 FireRedASR2 对完整音频重新识别，目标是准确。该模型中文普通话平均字错率约 2.89%，代价是不支持流式且有时长限制，需要分段处理。
对齐与融合。以第一遍的词级时间戳为骨架，将第二遍的结果对齐回同一时间轴，用高精度结果替换低精度文本，时间戳保持不变。最终产物是一份“当时就能跟上、事后足够准确”的带时间轴文本。
两遍结果的差异本身也是有价值的信号：如果某个段落在两遍识别中分歧很大，通常说明该段音频质量差、语速快或术语密集，这与认知负荷高度相关，可直接作为负荷特征之一。
5.2 卡点识别算法
这是本方案的核心。设计目标有三条：开销要低，可全程运行；解释要清楚，用户能理解为什么这里被标记；要能越用越准，支持个人化校准。
5.2.1 认知负荷计算
认知负荷回答的是“这段内容本身有多难”，与用户行为无关。它在课后批处理阶段计算，以 60 秒为窗口、15 秒为步长滑动覆盖全课程。五个特征如下。
<<TABLE>>
| 特征 | 符号 | 计算方式 | 直觉 |
| 术语密度 | TD | 窗口内首次出现的领域术语数 ÷ 总词数 | 新概念越多越难 |
| 语速偏移 | SS | 窗口语速 ÷ 全课平均语速 | 越讲越快越难跟 |
| 句长 | SL | 窗口内平均分句长度（按语音停顿切分） | 长句难解析 |
| 符号密度 | SD | 数学符号、代码标识、公式片段 ÷ 总词数 | 抽象符号增加负荷 |
| 停顿结构 | PS | 大于 1.5 秒的长停顿频次 | 教师思考或板书，信息负载高 |
<<END TABLE>>
各特征先做课程内 z-score 归一化，即以本课程自身的分布为基准，而不是用绝对阈值。这样不同语速、不同学科的课程之间具有可比性。
归一化后加权求和，经 sigmoid 压缩到 0 至 1：
<<TABLE>>
| L = sigmoid(0.35·TD + 0.25·SS + 0.15·SL + 0.15·SD + 0.10·PS) |
<<END TABLE>>
权重初始值来自领域经验，后续由行为数据校准（见 5.2.6）。需要强调：这一步不需要大模型参与。术语识别可采用领域词表加词性规则，符号密度用正则匹配，语速与停顿直接来自转写时间戳。整门课的认知负荷曲线计算耗时在秒级以内。
5.2.2 行为信号归一化
行为信号回答的是“用户在这段的真实反应”。系统采集以下事件：
<<TABLE>>
| 事件 | 含义 | 强度权重 |
| 回退跳转 | 用户主动往回拖 | 随跳转距离递增，0.6 至 1.0 |
| 重复播放 | 同一区间播放两次以上 | 0.8 |
| 停留超时 | 停留时长超过音频时长的 1.5 倍 | 0.7 |
| 降速 | 倍速从 1.25 以上降到 1.0 以下 | 0.5 |
| 失焦暂停 | 窗口失焦且暂停超过 60 秒 | 0.3 |
| 外部检索 | 切换到浏览器并搜索相关词（需授权） | 0.6 |
<<END TABLE>>
所有事件在时间轴上按窗口累加，取窗口内最大强度并做时间衰减（越靠近窗口中心权重越高），归一化到 0 至 1，记为 B。
小幅度回退（数秒内）通常是确认细节，大幅度回退（超过 30 秒）通常是整段没跟上，两者权重不同，这一点在工程上必须区分。
5.2.3 四象限判定
将认知负荷 L 作为纵轴、行为信号 B 作为横轴，得到四个象限。
<<TABLE>>
| 象限 | 条件 | 判定 | 处理 |
| 显性卡点 | L 高 且 B 高 | 已确认 | 直接入待解决队列 |
| 隐性卡点候选 | L 高 且 B 低 | 待确认 | 进入证据收集流程 |
| 个人因素 | L 低 且 B 高 | 非内容原因 | 降权，不主动提示 |
| 忽略 | L 低 且 B 低 | 正常 | 不处理 |
<<END TABLE>>
这个划分的关键作用是抑制误报。“回退了”并不等于“没听懂”，也可能是走神后回来、被消息打断、或想再看一眼板书。只有当回退发生在高负荷段落时，才可以高置信度地判定为卡点。
5.2.4 融合评分
<<TABLE>>
| S = 0.6·L + 0.4·B |
<<END TABLE>>
分级规则：S 大于等于 0.65 为强卡点，介于 0.45 与 0.65 之间为中等，低于 0.45 不标记。
权重设计上刻意让内容负荷占更大比重，原因是在冷启动阶段行为数据稀疏，若过度依赖行为会导致大量漏报。宁可多标，不可漏标——漏掉一个真实卡点的代价远高于多标一个候选。
5.2.5 隐性卡点的三种确认机制
隐性卡点的本质困难是：用户不知道自己不知道。因此不能依赖用户主动反馈，需要三种低成本机制来收集证据。
机制一，事后证据（迟到确认）。当某个高负荷段落在后续课程中被再次提及，而用户在再次提及处出现回退；或该术语出现在用户的截图提问与课后问答中——此时回填确认。这个机制不产生额外计算，只是等待证据自然出现。它同时捕捉到了一类重要现象：有些概念当时不觉得难，是后续内容让它暴露出来的。
机制二，抽样自测（主动探测）。每节课从“高负荷但无异常行为”的段落中随机抽取三个，课后以一个问题的形式请用户一句话复述。答不出即确认，答出即排除。每次只问三个，用户负担极低；系统用极少量采样换取高置信度，避免全量追问带来的疲劳。
机制三，跨课对账（结构性根因）。将各课程的知识点抽取后建立本地知识图谱，统计同一前置概念在多门课程中的出现与卡点位置。若某概念在三门课中均出现关联卡点，则判定为结构性卡点，并作为根因提示。该机制在夜间空闲时段增量执行，每次仅处理新增内容。
5.2.6 冷启动与权重校准
系统不训练神经网络，只校准权重。维度低、样本需求小、结果可解释。
第 1 至 3 节课：纯行为阶段。此时 L 的权重取初始经验值，B 由真实事件驱动。用户在课程结束时的处置行为（是否点开重讲、是否标记已掌握）作为天然标签。
第 4 节课起：启用在线校准。每次用户对卡点给出明确反馈（确认有用，或标记“这个我会”），执行一次权重更新：
<<TABLE>>
| w_i ← w_i + η · (y − ŷ) · x_i |
<<END TABLE>>
其中 y 为真实标签（1 表示确实卡住，0 表示已掌握），ŷ 为当前预测，x_i 为特征值，学习率 η 取 0.05。样本量少于 20 时以初始权重为主、更新幅度减半；超过 100 后趋于稳定。
校准的结果落在个人层面：同一段内容，对基础薄弱的学生判为强卡点，对已有基础的学生判为可忽略。这是“因材施教”在工程上的最小实现。
5.2.7 核心流程伪代码
<<TABLE>>
| for window in sliding_windows(transcript, size=60s, step=15s): 　　# 1. 认知负荷：纯统计，不调用模型 　　feats = extract_features(window)　　　　　# TD, SS, SL, SD, PS 　　z　　 = znorm_within_course(feats) 　　L　　 = sigmoid(dot(W_load, z)) 　　# 2. 行为信号：来自播放器事件流 　　B　　 = normalize_behavior(events_in(window)) 　　# 3. 融合与分级 　　S　　 = 0.6 * L + 0.4 * B 　　if S >= 0.65:　　label = "strong" 　　elif S >= 0.45:　label = "medium" 　　else:　　　　　　 continue 　　# 4. 四象限判定 　　if L > 0.5 and B > 0.5:　　 quadrant = "explicit" 　　elif L > 0.5 and B <= 0.5:　quadrant = "implicit_candidate" 　　else:　　　　　　　　　　　　quadrant = "personal" 　　emit_knot(window, S, quadrant, evidence=explain(z, events_in(window))) |
<<END TABLE>>
注意最后一行：每个卡点都要附带可解释的依据——是术语密度高、还是语速突增、还是你回退了两次。用户能看懂为什么这里被标记，才会信任系统。
5.3 时间轴对齐
所有信号必须落在同一条时间轴上，这是整个系统的地基。转写提供词级时间戳，Qwen3-ASR 配套的对齐模型可做到数十毫秒级；音频事件、情感标签、说话人切换均来自同一段音频，天然对齐；屏幕帧带有采集时刻，映射到播放进度；播放事件本身即带播放进度戳。
以播放进度为主轴而非墙钟时间，可以正确处理暂停、倍速与拖动带来的偏移。
5.4 数据模型
<<TABLE>>
| 表 | 关键字段 | 用途 |
| sessions | id, course_id, title, duration, created_at | 一次听课记录 |
| segments | session_id, idx, t_start, t_end, text, speaker, load_score | 转写切片与负荷 |
| events | session_id, t, kind, payload_json | 播放行为事件流 |
| knots | id, session_id, t_start, t_end, level, score, quadrant, evidence, status | 卡点 |
| knowledge_points | id, name, session_ids, first_seen_t, occurrences | 知识点与出现位置 |
| feedback | knot_id, action, ts | 用户对卡点的处置，用于权重校准 |
<<END TABLE>>
knots 表的 level 取值为显性、隐性、结构三类；status 取值为待解决、已重讲、已掌握。feedback 表是校准的数据来源，也是验证算法效果的真实标签。
5.5 调度策略
<<TABLE>>
| 阶段 | 触发时机 | 执行内容 | 资源占用 |
| 听课中 | 全程 | 采集 + 实时转写 + 事件记录，不做分析 | 约 5 GB，低功耗 |
| 课后批处理 | 用户结束课程后 | 精转、认知负荷计算、融合判定、候选生成 | 约 12 GB，1 至 3 分钟 |
| 夜间对账 | 空闲时段 | 知识点图谱更新、跨课关联、迟到确认回填 | 约 8 GB，增量 |
| 按需重讲 | 用户触发 | 加载 122B 主脑，生成降维重讲 | 约 85 GB，冷启半分钟 |
<<END TABLE>>
这套调度保证了一件事：系统永远不会和用户抢算力。用户在听课，它只记录；用户离开，它才开始思考。

六、关键设计决策记录
ADR-001　检测与理解分离
<<TABLE>>
| 字段 | 内容 |
| 状态 | 已采纳 |
| 上下文 | 若让大模型逐段判断“这段难不难”，一节 45 分钟的课需要数十次调用，本地无法满足延迟，云端成本无法承受。 |
| 决策 | 卡点检测使用规则与统计，常驻且轻量；大模型只在用户触发重讲或课后诊断时介入。 |
| 理由 | 认知负荷是可量化的文本统计特征，不需要语义理解即可近似。真正需要理解的是“这段在讲什么”，而那只在少数片段上发生。 |
| 后果 | 检测在 CPU 上即可运行，可全程常驻；代价是检测精度依赖特征设计，需要持续调优。 |
<<END TABLE>>
ADR-002　双遍转写
<<TABLE>>
| 字段 | 内容 |
| 状态 | 已采纳 |
| 上下文 | 流式模型延迟低但精度有损，高精度模型无法实时。 |
| 决策 | 实时用 1.7B 流式，课后用 8.3B 精转，按时间戳对齐融合。 |
| 理由 | 把“速度”与“精度”这对矛盾按时间轴拆开，而不是在单一模型上妥协。 |
| 后果 | 需要额外一次转写成本（课后几分钟），换来既跟得上又足够准的结果。两遍结果的差异本身可作为负荷特征复用。 |
<<END TABLE>>
ADR-003　不做自动播放与自动切集
<<TABLE>>
| 字段 | 内容 |
| 状态 | 已采纳 |
| 上下文 | 早期方案曾考虑“自动播放下一集”以提升连续学习体验。 |
| 决策 | 放弃该功能。 |
| 理由 | 其一，页面自动化不属于 AI 能力，与作品定位不符；其二，主流网课平台普遍设有防挂机机制（定时弹题、随机暂停、人脸抓拍），自动播放会被判为刷课行为，存在账号风险与合规风险；其三，自动切集消除了消化间隔，反而损害学习效果。 |
| 后果 | 改为“学习节拍器”方向——不替用户播放，而是在关键处停下、在已掌握处允许跳过。功能复杂度上升，但定位清晰。 |
<<END TABLE>>
ADR-004　静默运行，课后交付
<<TABLE>>
| 字段 | 内容 |
| 状态 | 已采纳 |
| 上下文 | 实时反馈看起来更有“智能感”，但会频繁打断注意力。 |
| 决策 | 听课全程无弹窗、无播报，所有结果课后一次性呈现。 |
| 理由 | 沉浸感来源于不被打断，而非自动化程度。持续打断会破坏学习状态，而学习状态是本产品唯一要保护的东西。 |
| 后果 | 演示时缺少“实时炫技”效果，需要在赛后材料中用时间轴回放来体现过程价值。 |
<<END TABLE>>
ADR-005　不做逐客户端适配
<<TABLE>>
| 字段 | 内容 |
| 状态 | 已采纳 |
| 上下文 | 课程分布在浏览器与十余种客户端中，若为每种平台单独开发采集适配，每次平台改版都需跟进。 |
| 决策 | 采集统一在操作系统层完成，不编写任何平台专用适配器；浏览器扩展只作可选精度增强。 |
| 理由 | 操作系统视角下两类载体没有本质差异，音频与画面均可统一获取。适配器清单会随平台数量线性膨胀，而采集底座一次投入即覆盖全部。 |
| 后果 | 客户端场景下播放进度与回退事件需由推断得出，精度低于浏览器直读；这是换取覆盖广度与可维护性的代价。带版权保护的播放器无法截取画面，自动降级为纯音频模式，核心能力不受影响。 |
<<END TABLE>>
七、合规与风险
7.1 学术诚信边界
产品定位必须清晰：帮用户听懂，不帮用户完成。
明确不做四件事：代写作业、代答试题、考试期间辅助、直接输出可直接提交的答案。F3 截图功能默认输出“该往哪看”而非“答案是什么”，答案置于可展开的第二层，并附带知识点定位。
理由不止于合规。真正稀缺的能力是“把题目和课程内容对上”，而非“会解题”——后者任何通用模型都能做，前者只有掌握用户课程上下文的系统才能做。
7.2 平台规则
不接管播放器、不注入脚本、不绕过任何平台限制。采集仅针对用户自己有权访问的内容，且仅在用户主动开启时进行。演示与测试一律使用用户自己录制的本地视频，不使用平台页面，避免被误认为刷课工具。
7.3 隐私设计
系统的角色是审计员，而非监听者。
不做 24 小时模型分析，仅在课程结束后批量处理已转写文本与少量片段；原始音频可配置为课后删除，仅保留转写文本与时间戳；屏幕画面仅在用户主动截图时高分辨率采集，常规分析使用低频采样；行为日志、卡点记录、知识图谱一律本地存储，不上传；若切换到云端 API，界面明确提示当前哪些数据将离开本机，并默认关闭音频上传。
7.4 技术风险
<<TABLE>>
| 风险 | 影响 | 应对 |
| 中文 ASR 对术语识别不稳 | 术语密度特征失真 | 引入课程级热词表，课后精转阶段修正 |
| 主脑冷启动慢 | 重讲响应变慢 | 预加载策略：用户停留超过阈值时预热 |
| 视觉 token 开销大 | 截图分析的预填充变慢 | 图像降分辨率、区域裁剪、仅送必要部分 |
| 权重校准过拟合 | 个别课程误判 | 设置更新上限，保留人工纠正入口 |
| 音频回环采集兼容性 | 部分设备无法采集系统音频 | 优先支持本地文件与浏览器音频流，逐步扩展 |
<<END TABLE>>
八、实施计划
8.1 MVP 边界
第一版只做三件事，其余全部推后。
<<TABLE>>
| 优先级 | 功能 | 完成标准 |
| P0 | 卡点识别（显性 + 隐性候选） | 一节真实课程能产出可解释的卡点清单 |
| P0 | 划段重讲 | 选中时间段后 15 秒内给出降维重讲 |
| P1 | 课后漏洞地图 | 生成含时间分布与复习顺序的诊断页 |
<<END TABLE>>
明确不在 MVP 内：自动播放、多课程管理、多人协作、移动端。
8.2 阶段划分
<<TABLE>>
| 阶段 | 目标 | 关键交付 |
| 阶段一 | 打通本地管线 | 音频采集、转写、事件记录、时间轴可视化 |
| 阶段二 | 实现卡点识别 | 认知负荷计算、四象限判定、卡点清单 |
| 阶段三 | 实现重讲与截图对回 | 五种重讲策略、知识点检索、课程定位 |
| 阶段四 | 打磨与验证 | 权重校准、漏洞地图、演示脚本、指标测量 |
<<END TABLE>>
8.3 验证方法
算法效果必须可测量，否则无法证明。
构造测试集。自行录制 10 节真实课程，覆盖不同学科与不同讲师，在听课过程中记录真实回退与真实困惑，形成人工标注的卡点真值。
<<TABLE>>
| 指标 | 定义 | 目标 |
| 召回率 | 真值卡点中被系统标记的比例 | 大于 0.8 |
| 精确率 | 系统标记中确为真实卡点的比例 | 大于 0.6 |
| 标记延迟 | 用户回退到标记出现的时间 | 小于 3 秒 |
| 隐性检出率 | 隐性卡点候选经抽样自测确认的比例 | 大于 0.5 |
<<END TABLE>>
召回率优先于精确率：漏报的代价是用户继续听不懂，误报的代价只是多一条待确认记录。
对照实验。同一节课分别用“仅行为信号”与“行为 + 负荷融合”两种策略运行，比较精确率提升幅度，用以验证融合设计的实际价值。
九、创新点总结
第一，检测与理解分离的算力架构。把“判断哪里难”与“讲明白难在哪”拆给不同量级的模型，使端侧实时运行成为可能。这是本方案能在消费级硬件上成立的根本原因。
第二，迟到确认机制。隐性卡点不靠猜测，而靠后续课程中的证据回填。它捕捉到了“当时不觉难、后来才暴露”这一类被所有工具忽略的漏洞。
第三，降维重讲而非复述。同一概念按类比、前置、数值、反向、分层五种路径重新组织，把“再讲一遍”变成“换一条路讲”。
第四，长期个人学习档案。跨课程、跨学期的卡点与知识点图谱，使系统随使用逐步贴近个体认知结构，且这份资产完全留在本地，构成云端方案无法复制的护城河。
附录 A：术语表
<<TABLE>>
| 术语 | 含义 |
| 卡点 | 用户未能理解的具体时间位置及其认知缺口 |
| 认知负荷 | 内容本身的难度度量，由文本与语音统计特征计算得出 |
| 行为信号 | 用户播放行为所反映的真实反应，如回退、重复播放 |
| 显性卡点 | 有明确行为证据的卡点 |
| 隐性卡点 | 内容负荷高但当时无异常行为，需后续证据确认的卡点 |
| 结构性卡点 | 跨多门课程反复出现的同一类前置知识缺口 |
| 迟到确认 | 卡点在后续课程中被再次触发后才获得确认的机制 |
| 降维重讲 | 通过改变讲解路径降低理解门槛，而非重复原有讲法 |
<<END TABLE>>
